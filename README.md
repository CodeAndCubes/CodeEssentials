# CodeEssentials

Серверный набор перемещений для Minecraft 1.7.10: дома с лимитом из прав, варпы с нодой на каждый,
спавн по измерениям, возврат `/back`, tpa-запросы, случайный перенос и киты. Все переносы, от `/home`
до респауна, идут через один движок с тёплой задержкой, поиском безопасной точки и кулдаунами.

Мод подаёт заявку на роль `essentials` в реестр адаптеров CodeCore и держит её целиком: дома, варпы,
спавн, `/back` и tpa. Кто держит роль, решает секция `[owners]` главного файла линейки. Хранилище
состояния игроков и политика поиска безопасной точки открыты через SPI: своё хранилище или свои
правила приземления подключаются без правки кода мода.

Клиентской части нет: ванильный клиент заходит на сервер с CodeEssentials без этого мода.

## Требования

- Minecraft 1.7.10, запуск на Java 8.
- CodeCore 0.1.0 или новее, зависимость `required-after:codecore`.

## Сборка

Нужен JDK 25 (версию демона задаёт `gradle/gradle-daemon-jvm.properties`), wrapper скачает Gradle
сам. Байткод собирается под Java 8 через jabel, поэтому мод грузится на обычной 1.7.10.

```
./gradlew build
```

В `build/libs` появятся универсальный `CodeEssentials-0.1.0.jar` для dev-запусков и
`CodeEssentials-0.1.0-server.jar` для сервера. Раздавать универсальный jar игрокам нельзя: в нём
есть серверный код.

## Подключение

1. Собрать и опубликовать зависимости локально: `CodeSides` и `CodeCore` через `publishToMavenLocal`.
2. Здесь: `./gradlew build`.
3. На сервер в `mods` положить `codecore` и `CodeEssentials-0.1.0-server.jar`.

Настройки лежат в `config/code/essentials/`: `essentials.toml`, `essentials-commands.toml` с
включением и алиасами корней команд, `essentials-warps.toml`, `essentials-spawn.toml` и
`essentials-kits.toml` правятся человеком. Дома, стек возврата, буфер китов и кулдауны живут в мире,
в `<мир>/code/essentials/essentials-players.json` и `essentials-rates.json`, и переезжают вместе с
папкой мира.

Число домов, длина тёплой задержки и кулдауны причин стоят не здесь, а в главном файле линейки
`config/code/config.toml`, секция `[essentials]`. Там же общие для линейки `[storage]` и `[audit]`.
В `essentials.toml` остаётся редкое: потолки `limits`, поведение прогрева, поиск безопасной точки,
режим `/back` и параметры tpa-запросов.

Ноды прав со списком команд: [perms.md](perms.md).

## Чужой essentials-мод на том же сервере

Имена команд у всех модов этого рода одинаковые, и в 1.7.10 порядок регистрации решает, кто
выиграет `/home`. Решать должен администратор, поэтому в `config/code/essentials/essentials-commands.toml`
на каждый корень заведена запись с двумя полями.

```toml
[commands.tp]
enabled = false
aliases = []

[commands.home]
enabled = true
aliases = ["casa"]
```

- `enabled: false` не регистрирует корень вовсе, поэтому имя остаётся свободным для чужого мода, а
  игрок видит ванильный ответ про неизвестную команду, а не отказ по праву. В лог уходит строка
  `Command root tp is off in essentials-commands.toml, the name stays free`.
- Список `aliases` заменяет заводской целиком, пустой список оставляет корень без алиасов. Заводские
  алиасы всего два: `tpyes` у `/tpaccept` и `ess` у `/essentials`.

Файл создаётся при первом запуске со всеми корнями, включёнными и с заводскими алиасами: правка
делается по месту, а не вслепую. Три вещи, которые стоит знать заранее:

- Незнакомое имя корня (опечатка, корень из будущей версии) пропускается с записью в лог и остаётся
  в файле. Мод чужие строки не трогает: предупреждение будет повторяться при каждом старте, пока
  строку не уберёт человек.
- Новый корень, которого в файле ещё нет, дописывается заводской записью и файл сохраняется, чтобы
  было что править.
- Алиас, совпадающий с именем другого включённого корня, принимается, но в лог уходит
  предупреждение с обоими именами: кто в итоге получит имя, решает порядок регистрации на сервере.

Таблица команд отдаётся серверу один раз, на `FMLServerStartingEvent`. `/essentials reload`
перечитывает `essentials-commands.toml` с диска, но зарегистрированные команды после этого не
меняются: правки корней вступают в силу после перезапуска, и ответ команды об этом говорит. Смена
владельца роли в `[owners]` тоже ждёт перезапуска, и ответ называет её отдельной строкой.

## Киты

Кит это раскладка предметов по слотам инвентаря игрока: 0..8 хотбар, 9..35 рюкзак, 36..39 броня
(сапоги, штаны, нагрудник, шлем). Заводится тремя дорогами: руками в `essentials-kits.toml`,
командой `/kit save <имя>` (снимает собственный инвентарь админа с сохранением слотов) и редактором
`/kit edit <имя>` (виртуальный сундук, правки сохраняются при закрытии). Удаляется отдельной командой
`/kit delete <имя>`; пустой кит записать нельзя ни одной дорогой.

```toml
[kits.starter]
once = false
cooldownSeconds = 3600

[kits.starter.slots]
"0" = "minecraft:stone_sword"
"1" = "minecraft:bread 16"
"2" = "minecraft:iron_pickaxe 1 120"
"39" = "minecraft:iron_helmet 1 0 {display:{Name:\"Стартовый шлем\"}}"
```

Запись предмета: `имя [число] [урон] {nbt}`. Имя без префикса читается как `minecraft:`, число больше
стака разворачивается в несколько стопок, NBT пишется строкой в фигурных скобках в конце.

`/kit <имя>` выдаёт кит тому, у кого есть нода `codeessentials.kit.<имя>`; `/kits` показывает все киты
с состоянием каждого (доступен, через сколько, взят навсегда, ждёт в буфере), закрытые правом помечены.
`/kit give <ник> <кит>` под `codeessentials.admin.kit` выдаёт кит другому: онлайн получает обычной
доставкой, офлайн кладёт всё в буфер. `/kit edit`, `/kit save`, `/kit delete` и `/kit give` живут под
одной нодой `codeessentials.admin.kit`.

Выдача никогда не выкидывает и не удаляет предметы. Порядок доставки предмета: свой слот, затем
слияние с существующими стопками, затем первый свободный слот инвентаря, затем персональный буфер
этого кита. Предмет из клетки брони идёт только в свой слот брони и только если предмет туда
надевается, иначе ждёт в буфере. Ничего не влезло, лежит в буфере и доезжает при следующем `/kit`:
долг доставляется без траты нового получения, без проверки права и без вето. Получение с полностью
занятым инвентарём считается состоявшимся: кит целиком уходит в буфер, одноразовость отмечается,
кулдаун идёт. При входе игрок с непустым буфером получает напоминание с числом предметов;
автоматической выдачи на входе нет.

`once` и `cooldownSeconds` независимы. Ноль у паузы значит «без кулдауна», и тогда метка прошлого
получения никого не держит. Отсчёт идёт по реальному времени и переживает рестарт. Нода
`codeessentials.bypass.cooldown` снимает и паузу кита, но не отметку одноразового. Удалённый кит
отвечает «не существует», буфер при этом лежит в мире: вернувшийся под тем же именем кит доносит долг.

## Тёплый телепорт и что его снимает

`/home`, `/spawn`, `/warp`, `/back` и принятый tpa ждут `[essentials] warmupSeconds` главного файла
(3 секунды).
Задержку снимает сдвиг дальше `teleport.warmupMoveRadius` (2 блока по горизонтали, 1 по вертикали),
полученный урон, смерть, выход с сервера, `/ecancel` и вето чужого мода. Поворот камеры не считается
движением.

Движение ловится опросом позиции на серверном тике, а не событием, поэтому поездка верхом, в
вагонетке или на лодке снимает перенос ровно так же, как ходьба: игрок сдвинулся, значит задержка
не выдержана. Это ожидаемое поведение, а не бага. Нужен перенос без задержки, поставьте
`[essentials] warmupSeconds` в 0 или выдайте персональную мету `codeessentials.warmup`.

Административные `/tp` и `/tppos` задержки не ждут вовсе, кулдаун не списывают и работают от
консоли и командного блока.

## Границы: чужие переносы и консоль

- Чужой мод двигает игрока в обход движка (портал, свой телепорт, ванильная `/tp`): модель одной
  работы на игрока от этого не защищает. Стек `/back` может зафиксировать точку, поставленную чужим
  переносом, а идущий тёплый телепорт снимется причиной «вы сдвинулись». Это известная граница
  первой версии.
- Свой кроссмирный перенос мода поднимает то же событие смены измерения, что и чужой, поэтому движок
  отличает их по состоянию работы: пока перенос идёт сам, стоящая в слоте работа не гасится.
- `/setwarp` и `/setspawn` от консоли и командного блока недоступны: обе команды берут точку от
  отправителя, а у консоли позиции нет. Ответ такой же, как у `/home`: `codeessentials.error.sender_not_player`.
  Варпы и спавн правятся файлами `essentials-warps.toml` и `essentials-spawn.toml`, `/delwarp` консоли доступен.
- Прокси (BungeeCord и подобные) сознанная не-цель: мод работает как обычный Forge-мод на одном
  сервере.

## Подмена сервисов

`TeleportService`, `HomeService`, `WarpService`, `SpawnService`, `BackService` и `KitService`
регистрирует за владельцем роли `essentials` само ядро, вес оно тоже выбирает само. Хранилище игроков
`PlayerDataStore` и политика точки `SafeSpotPolicy` роль не закрывает, они встают весом `BUILTIN`.
Порядок такой:

1. В фазе `init` мод объявляет роль и подаёт заявку именем `codeessentials`.
2. В конце постинициализации ядро читает `[owners] essentials` главного файла и выбирает владельца:
   `auto` берёт наш мод, `off` не берёт никого, имя берёт названного.
3. Реестр замораживается, после этого состав не меняется.
4. Кто чем владеет, видно в логе строкой `Services: TeleportService ..., HomeService ..., KitService ...`.

Роль ушла не нам: мод отходит целиком. Ни корней команд, ни файлов игроков и кулдаунов, ни
подписок, ни фонового писателя. Существующие файлы остаются нетронутыми, в лог уходит одна строка.
Вернули `essentials = "auto"`, перезапустили, всё на месте.

Хранилище состояния игроков и политика поиска точки подменяются иначе, без роли: через
`EssentialsApi.registerStore` и `EssentialsApi.registerPolicy` до заморозки, а выбор делается по
имени в `[storage] provider` главного файла и в `safeSpot.policy` своего. Провайдера с таким именем
нет: мод пишет строку в лог и работает на встроенном json.
